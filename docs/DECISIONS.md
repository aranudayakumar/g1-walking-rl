# Decisions

Record material project choices here. This is not append-only; superseded decisions should remain visible and be marked superseded.

## ADR-001 — Training/framework path
Status: decided (2026-09-18).

Context:
The challenge asks for Unitree G1 locomotion with MuJoCo and links Unitree/Berkeley references. Machine audit: Apple M5 Pro (arm64 macOS 26.5.2), no NVIDIA GPU/CUDA, 24GB RAM, 15 CPU cores, system Python 3.14.6.

Options researched (re-verified 2026-09-18 against live repo READMEs/docs, not assumed from the challenge doc):
1. official `unitreerobotics/unitree_rl_gym` — trains via **Isaac Gym** (`legged_gym/scripts/train.py`), requires an Nvidia GPU + Linux per its own setup docs. MuJoCo appears only as "Sim2Sim" post-training deployment validation (`deploy/deploy_mujoco/`), never as the training backend. Last push 2025-07-25 (stale). No macOS/CPU training path exists.
2. official `unitreerobotics/unitree_rl_mjlab` (wraps `mujocolab/mjlab`, algorithm=`rsl_rl`) — mjlab's own README states verbatim: "mjlab requires an NVIDIA GPU for training. macOS is supported for evaluation only." It uses MuJoCo **Warp** (GPU-native), not MJX-on-CPU. Both repos are actively maintained (mjlab pushed 2026-09-17) so this is current, not lagging documentation — it is a hard architectural requirement, not a soft recommendation.
3. Direct MuJoCo + Gymnasium + a maintained PPO library (stable-baselines3) — native MuJoCo wheels support macOS arm64 directly; SB3 is pure PyTorch/NumPy and runs on CPU everywhere (known caveat: SB3 does not reliably use Apple MPS, so plan `device="cpu"` explicitly, not MPS — see DLR-RM/stable-baselines3#914). `rsl_rl` used standalone (outside mjlab/Isaac) would need a vectorized-env adapter, more integration work than SB3 for a single-machine CPU setup.

Corroborating local evidence: two mature sibling projects on this same machine (`../standing-rl`, `../walking-rl`) already independently converged on exactly this path — MuJoCo + Gymnasium custom env + stable-baselines3, Python 3.12 venv, `device: cpu`, vendored G1 MJCF from `mujoco_menagerie` — and it runs today (mujoco 3.12–3.13, gymnasium 1.3.0, torch installed, PPO configured with `n_steps=512`, `batch_size=256`, `[256,256]` MLP). This independently validates path 3's feasibility on this exact hardware before we wrote any code ourselves.

Decision:
Direct **MuJoCo + Gymnasium + stable-baselines3 (PPO)**, Python 3.12 venv (not the system 3.14 — SB3/torch/mujoco wheels do not yet support 3.14, confirmed by `pip install` attempts failing on 3.14 in sibling projects' own setup notes and by current SB3/torch release support matrices).

Why:
Paths 1 and 2 are hard-blocked by upstream design choices (Isaac Gym; MuJoCo Warp/CUDA) that are current as of today's re-verification, not stale docs. Path 3 is the only one with a documented, working CPU-native macOS story, and it is de-risked by two already-working local reference implementations for the identical robot on the identical machine.

Rejected alternatives:
- `unitree_rl_gym`: no Nvidia GPU available; MuJoCo is not its training backend.
- `unitree_rl_mjlab`/`mjlab`: GPU required for training by the framework's own documentation; macOS is evaluation-only.
- Reimplementing PPO by hand: unnecessary and against the challenge's explicit instruction to use a maintained trainer.

Consequences:
- We own the Gymnasium environment, reward, termination, and reset logic ourselves (no pre-built G1 task config), unlike option 2 which ships one.
- G1 MJCF/meshes vendored from `mujoco_menagerie` (via the already-vetted copy in `../standing-rl/assets/g1`, itself fetched from `google-deepmind/mujoco_menagerie` commit `da76818e269b82289eba39808e2fb91d679d6994`) rather than re-fetched, to avoid re-verifying provenance from scratch. License: Unitree/BSD-style, permissive for this vendored copy (see `assets/g1/LICENSE`).
- Training throughput is CPU-bound; runs must stay small (short smoke tests, then bounded baseline runs) per `CLAUDE.md` fast-iteration guidance. GPU convergence is explicitly named an "optional open challenge" in the source document, not a requirement here.

Fallback:
If stable-baselines3 PPO integration hits a blocking issue, fall back to `rsl_rl` used standalone against our own Gymnasium env (more integration work, same CPU constraint) before reconsidering GPU-only paths.

## ADR-002 — Environment scope: controlled DoFs, observation, action, reward
Status: decided (2026-09-18).

Context:
The challenge asks for observation/action space definition and a minimal reward, without prescribing exact dimensionality. G1 has 29 actuated joints (12 leg, 3 waist, 14 arm/wrist).

Decision:
- **Controlled DoFs**: only the 12 leg joints (hip x3, knee, ankle x2, per leg). Waist and arms are held at the upstream `g1.xml` "stand" keyframe pose via MuJoCo's own position actuators, not RL-controlled.
- **Actuation**: convert the 12 leg `<position>` actuators to `<motor>` (direct torque) in a derived model `assets/g1/g1_walk.xml` (`scripts/build_walk_model.py`), so a PD law we own converts policy position-targets to torque, matching the challenge's stated action semantics ("target joint positions as outputs").
- **Observation** (44-dim, `envs/observations.py`): leg joint pos relative to default (12) + leg joint vel (12) + base angular velocity, body frame (3) + projected gravity, body frame (3) + commanded (vx, vy) (2) + previous action (12). Matches the challenge doc's listed fields exactly; base *linear* velocity is deliberately excluded from the observation (privileged/hard to estimate on hardware) even though it is used to compute the reward.
- **Command**: 2D (vx, vy) sampled uniformly once per episode, no yaw/turning command yet (minimal first version).
- **Reward** (`rewards/walking_reward.py`): exactly the challenge's minimum — `tracking_lin_vel` (exp of squared base-frame velocity error) + `alive_bonus` (constant per step) + `torque_penalty` (sum of squared torque). No pose-imitation, no foot-slip, no orientation term yet.
- **Termination**: pelvis height < 0.5m, or projected-gravity z > -0.3 (tipped roughly >=70 deg from upright), or non-finite state. Truncation: 20s / 1000 control steps.

Why:
- Controlling only 12/29 joints matches common practice (unitree_rl_gym-style locomotion configs typically control the legs and hold the upper body fixed or lightly regularized) and keeps the action space minimal, per "smallest system that fully solves the problem."
- Reusing the motor-actuator conversion technique already validated in `../standing-rl` for the identical robot avoids re-deriving PD-vs-MuJoCo-position tradeoffs from scratch, while still being independently re-derived here (`scripts/build_walk_model.py`) rather than copied, so it's understood, not trusted blindly.
- Excluding base linear velocity from the observation follows the sim2real literature named in the challenge doc (Berkeley Humanoid, Radosavovic et al.) and the challenge doc's own listed observation fields, which omit it.

Evidence (`scripts/smoke_test_pd_hold.py`, `scripts/smoke_test_env.py`, 2026-09-18):
With zero policy action, the robot survives ~1.3s (65-66 control steps) before terminating on `fell_height`, falling forward via ankle-pitch tracking error growing past -0.4 rad around t=1s — expected for a free-standing biped with pure joint-space PD and no active balance feedback (not a bug; see docs/SIMULATION.md). This gives short but consistent initial episode lengths for PPO to learn against, and confirms termination triggers before the state goes numerically unstable.

Rejected alternatives:
- Controlling all 29 joints: larger action space with little payoff for a first "does it walk" pass; upper-body flailing does not help forward locomotion and is a known failure mode from `../walking-rl`'s more advanced (whole-body) attempts.
- Including base linear velocity in the observation: works fine in sim but contradicts the challenge's own field list and the referenced sim2real papers.
- Larger reward (foot-slip, orientation, action-rate terms) up front: explicitly against CLAUDE.md's "add a term only after naming a measured failure."

Consequences:
Revisit controlled-DoF scope, observation fields, and reward terms only after a specific measured failure motivates it (docs/FAILURE_ANALYSIS.md), per Phase 7 of PROJECT_PLAN.md.

## ADR-003 — Evaluation must include distance traveled, not just survival/reward
Status: decided (2026-09-18), methodological (not env/reward code, but a standing evaluation practice).

Context:
EXP-0006 (docs/FAILURE_ANALYSIS.md F-0002) tested capping PPO's `target_kl` to fix high-speed-command falls seen in the canonical baseline (`baseline0001`). By total reward (952.0 vs 947.1) and survival (20/20 vs 15/20 episodes reaching the 20s truncation), EXP-0006 looked like a strict improvement. Adding a distance-traveled metric revealed the opposite: EXP-0006's policy stands nearly motionless (5.1% of the commanded distance covered) while `baseline0001` actually walks (56.6% of commanded distance) despite its occasional high-speed falls.

Decision:
`evaluation/evaluate.py` always reports `distance_traveled_m` / `expected_distance_m` / `distance_ratio` (net pelvis xy displacement vs. commanded displacement) alongside reward, episode length, and termination reason. Any future claim that one checkpoint/config is "better" must check this metric, not just reward or survival.

Why:
A flat `alive_bonus` (and, more generally, any reward with a per-step term that does not itself require task progress) makes "not falling" achievable without doing the task. This is a known class of RL reward-hacking failure mode, and it was caught here empirically, not by anticipating it in advance -- worth encoding as a standing check rather than trusting it won't recur.

Consequences:
`baseline0001` (not `exp0006_target_kl`) is the canonical baseline specifically because of this check (docs/FAILURE_ANALYSIS.md F-0002, experiments/EXPERIMENT_LOG.md EXP-0006). Any future reward change should also be re-examined against this metric, especially changes to `alive_bonus` or termination leniency.

**Addendum (2026-09-18, after EXP-0008):** `distance_ratio` itself needed a second correction. EXP-0008's episodes averaged only 2.4s before falling, and produced a `distance_ratio` of 1.91 -- numerically the "best" value seen, despite being unambiguously the worst policy (falls every episode). Cause: `distance_ratio = traveled / (command * episode_length)`, and a tiny `episode_length` denominator makes a few lurching steps before a fall look like a huge fraction of "expected" distance. Fix (`evaluation/evaluate.py`): each episode now carries `distance_ratio_reliable` (true only if the episode reached at least half the max episode length, 10s of 20s here), and the aggregate `mean_distance_ratio_reliable_only` averages only over those episodes (`n_reliable_ratio_episodes` reports how many). Re-running this filter on the existing runs changed `baseline0001`'s reported ratio from 0.566 (all 20 episodes) to **0.479** (n=16 reliable episodes) and `exp0007_low_alive_bonus`'s from 0.421 to **0.337** (n=16) -- both went down, since the previously-included short failed episodes happened to inflate rather than deflate the naive average. The relative ranking (`baseline0001` > `exp0007` > `exp0006`/`exp0008`) is unchanged; only the absolute numbers are corrected. Historical experiment-log entries were not rewritten (`experiments/EXPERIMENT_LOG.md` is not to be rewritten to look cleaner after the fact) -- treat any `distance_ratio` number dated before this addendum as the pre-correction (all-episode) version, and anything from `results/compare.py` or a fresh `evaluation.evaluate` run after this point as the corrected (reliable-only) version.

## ADR-004 — Canonical baseline updated: more training, not reward/PPO-config changes, fixed F-0002
Status: decided (2026-09-18).

Context:
Three config-change experiments (EXP-0006 `target_kl`, EXP-0007 lower `alive_bonus`, EXP-0008 both combined) all failed to beat `baseline0001` (3M timesteps) on `mean_distance_ratio` -- two made things worse, one collapsed to a degenerate near-motionless policy. All three left the training *budget* unchanged at 3M timesteps, the same budget the original baseline used, and so never tested whether `baseline0001` was simply undertrained rather than misconfigured.

Decision:
EXP-0009 reran `baseline0001`'s exact, unmodified config for 10M timesteps (checkpointed every 2M) and evaluated the trend, not just the endpoint. Every checkpoint from 4M timesteps onward already beat `baseline0001`'s `dist_ratio` (0.479) by a wide margin (0.56-0.71). The training curve shows why: reward oscillates in a repeating climb-crash-recover pattern (consistent with the high `approx_kl`/`clip_fraction` seen throughout this project), trending upward in peak height over many cycles -- 3M timesteps was simply too early in that process. The 6M-timestep checkpoint (`experiments/runs/exp0009_longer_baseline/best_checkpoint_6M.zip`) is a strict improvement over `baseline0001` on every metric (length, reward, tracking error, distance, falls) and is now the **canonical baseline**.

Why:
This directly resolves F-0002's three-way open question (undertraining vs. PPO instability vs. reward shaping) in favor of undertraining as the dominant factor, while confirming the *diagnosis* of PPO instability was still correct -- the fix for it was not to suppress it (EXP-0006), but to train through enough oscillation cycles to reach a good peak, then select the checkpoint that evaluates best rather than trusting the final one.

Rejected alternative interpretation:
"PPO instability must be fixed at the algorithm-config level" (the premise behind EXP-0006/0008) -- rejected because directly suppressing it produced worse real-walking behavior, not better, and because untouched instability combined with a longer budget outperformed every stabilized variant tried.

Consequences:
- Checkpoint selection via deterministic evaluation across the training run (`evaluation/evaluate_checkpoints.py`, built for this experiment) is now a standing practice for any future run in this family -- the final-step checkpoint of a fixed-budget run is not guaranteed to be the best one, given this training dynamic.
- All deliverables (video, curves, writeup) updated to reference `exp0009_longer_baseline`'s 6M-step checkpoint, not `baseline0001`.
- The residual failure (falls concentrated at the highest commanded speeds, now 3/20 instead of 5/20) persists and is not yet fully explained -- an honestly-labeled remaining limitation, not a blocker.

## ADR-005 — Canonical baseline updated again: measured-then-calibrated gait-quality reward terms fixed heading drift
Status: decided (2026-09-18).

Context:
A user-reported concern ("does it walk straight or take steps?") led to a new diagnostic tool (`diagnostics/gait_diagnostic.py`) that found two problems invisible to every metric used so far: the canonical policy (`exp0009_longer_baseline`) drifted 95 degrees in 10 seconds under a pure-forward command (`tracking_lin_vel` is computed in the robot's own local frame, so nothing penalizes rotation), and took tiny (2.5cm), rapid (~5.5Hz) chattery steps rather than clean strides (docs/FAILURE_ANALYSIS.md F-0003).

Decision:
Added two reward terms directly motivated by these measurements: `ang_vel_penalty` (squared yaw rate) and `action_rate_penalty` (squared action delta). The first attempt (EXP-0010, `ang_vel_penalty=1.0` -- chosen by the unverified heuristic "same order as `tracking_lin_vel`'s own weight") collapsed the policy to near-total stillness (`dist_ratio` ~0.01 at every checkpoint) -- caught immediately by the ADR-003 standing practice, not missed. Rather than guess again, the actual gait's own yaw-rate statistics were measured directly (`exp0009`'s reference checkpoint replayed through the new reward math offline): its natural walking yaw wobble cost `-0.44/step` at weight 1.0, *exceeding* the `+0.80/step` mean tracking reward it was competing with -- explaining the collapse exactly. Recalibrated to `ang_vel_penalty=0.1` (EXP-0011) made the same gait's typical cost ~5% of the tracking reward instead of ~55%. Result: yaw drift cut by 88% (95 -> 11.6 deg/10s) in a controlled straight-line test, with no regression in survival, tracking error, distance traveled, or fall count. `experiments/runs/exp0011_gait_quality_v2/best_checkpoint_10M.zip` is now the **canonical baseline**.

Why:
This directly validates the ADR-003 discipline (checking `dist_ratio` caught EXP-0010's failure immediately, the same day the terms were added) and demonstrates the fix for a bad reward-weight guess: measure what the term actually costs the behavior you don't want to destroy, rather than picking another number by feel. "Same order of magnitude as another term" is not a substitute for measuring the actual quantity being penalized.

Consequences:
- `evaluation/evaluate.py` now also reports `mean_abs_yaw_drift_per_10s_deg` (and per-episode `yaw_drift_deg`/`yaw_drift_per_10s_deg`) for every future run, alongside `dist_ratio`; `results/compare.py` shows it in the standard comparison table.
- `diagnostics/gait_diagnostic.py` (trajectory, foot-height, foot-contact plots under a controlled fixed command) is now the standing tool for checking heading/stepping quality specifically, complementing the aggregate metrics which can miss it entirely (as they did for 5 straight experiments before F-0003).
- The chattery small-stride stepping pattern is only partially improved (stepping frequency down slightly, clearance essentially unchanged) -- an honestly-labeled open item, not claimed as fixed.
- Any future reward-weight choice in this project should follow the same measure-first pattern established here, not the "same order as another term" heuristic that caused EXP-0010's collapse.

**Addendum (2026-09-18, after EXP-0012/0013):** two further attempts at the chattery-stepping problem were made and both reverted -- `exp0011_gait_quality_v2` remains canonical. EXP-0012 added `feet_air_time_bonus` (reward a longer swing at touchdown, weight measured against `exp0011`'s own gait per this ADR's discipline) and it was gamed: the policy learned to skate (slide feet at ~0.25 m/s while staying in geometric contact) since a foot that never lifts never triggers a touchdown-only reward (docs/FAILURE_ANALYSIS.md F-0004). EXP-0013 added a complementary `stance_overrun_penalty` (also measure-first calibrated) to close that loophole structurally, and it made things categorically worse (100% fall rate at every checkpoint) -- the two terms fight over the same variable (when to step) with incompatible demands (lift soon vs. once lifted, stay up long), a failure mode individual-term calibration cannot detect. Both are documented, mechanistically-understood negative results -- see EXP-0012/EXP-0013. **Lesson beyond this ADR's own**: measuring a new term's cost against a reference gait validates that term in isolation, but does not validate a *combination* of new terms against each other -- an interacting pair can fail in ways neither term's individual calibration would predict.

## ADR-006 — Phase 8 domain randomization: implemented and verified, not yet adopted (needs more budget)
Status: decided (2026-09-18), in progress.

Context:
With `exp0011_gait_quality_v2` established as a robustly-working canonical baseline, PROJECT_PLAN.md Phase 8 (and the challenge document itself) call for domain randomization "once basic walking works." Implemented `envs/domain_randomization.py`: per-episode floor friction, global mass+inertia scale, motor-strength multiplier, and periodic velocity pushes, all disabled by default (every prior config unaffected, verified via a test that checks a disabled config consumes zero extra RNG draws).

Decision:
Trained `exp0014` (10M timesteps, same reward/PPO config as `exp0011`, domain randomization enabled with informed-but-untuned ranges) and evaluated under both clean and randomized physics, plus the critical control: `exp0011` itself evaluated under the same randomized physics it never trained on. Result: `exp0014` was worse than `exp0011` on *both* clean physics (expected trade-off) *and* randomized physics (not expected -- a policy trained for robustness should at least be more robust). Diagnosis, following the EXP-0009 precedent directly: 10M timesteps was sufficient for the much simpler non-randomized task but domain randomization multiplies the effective scenario space (friction x mass x motor-strength x push-timing) and plausibly needs substantially more budget to converge. `exp0015` (20M timesteps, otherwise identical) is testing this directly rather than concluding domain randomization doesn't help.

Why:
This mirrors ADR-004's own lesson almost exactly (three reward/config changes were tried and rejected before discovering `baseline0001` was simply undertrained) -- the discipline established there ("test budget as its own variable before concluding a technique doesn't work") applies just as much to domain randomization as it did to the base reward.

Consequences:
- `exp0011_gait_quality_v2` remains canonical while this is evaluated -- domain randomization is not deployed as a replacement until it demonstrates a clear robustness win without an unacceptable clean-performance cost.
- If EXP-0015's longer budget still doesn't show a benefit, the next lever is gentler randomization ranges or a curriculum (start clean, ramp up randomization over training) rather than a third blind budget increase -- see EXP-0015's own pre-registered stop condition.
- The randomization ranges themselves (friction x[0.5,1.5], mass x[0.85,1.15], motor strength x[0.7,1.0], pushes every 3-6s at 0.1-0.5 m/s) are informed starting points, not yet validated as the right magnitude -- revisit them with evidence if EXP-0015 also underperforms after ruling out budget as the cause.

**Resolution (2026-09-18, after EXP-0015):** the budget hypothesis was confirmed. Doubling to 20M timesteps produced a checkpoint that, under the randomized physics it was tested on, survives longer (13.9s vs. 10.9s) and falls less often (11/20 vs. 13/20) than `exp0011` (trained with zero randomization) evaluated on the identical randomized conditions -- a genuine, if modest, robustness gain, with more episodes running long enough for a reliable `dist_ratio` estimate (14 vs. 9). The trade-off is real, not free: `exp0015` tracks commanded velocity less precisely than `exp0011` on both clean and randomized physics (higher `vel_err`, lower `dist_ratio`). **Final decision: `exp0015_domain_randomization_long`'s 20M checkpoint is documented and kept as a working, more-robust *alternative*, not a replacement for the canonical baseline.** `exp0011_gait_quality_v2` remains canonical for the primary deliverable (better clean-condition tracking is what the challenge's own video/curves showcase); `exp0015` is the answer to "what if physics isn't exactly nominal," available with its trade-offs clearly stated. The clean-physics `dist_ratio` trend had not yet plateaued at 20M (0.18 -> 0.54 across the run), so even more budget is a plausible further lever, left as documented future work rather than pursued further given the time already invested (this single run took ~108 minutes).

**Second resolution (2026-09-19, EXP-0021, after the canonical baseline moved to `exp0017`):** `exp0015` was trained on top of the pre-EXP-0016 reward, so it was unclear whether its robustness gain would survive being combined with the later stepping-quality fix. Re-ran the identical randomization config on top of `exp0017`'s reward, this time via warm-start fine-tuning from `exp0017`'s own checkpoint (5e-5 LR) rather than from scratch -- both to save budget and to test whether the warm-start recipe (previously validated only for new reward terms, ADR-007/008) also works for a training-distribution change. Result: the same robustness trade-off pattern reproduced almost exactly on the better base gait -- randomized-physics falls roughly halved relative to the correct control (`exp0017` itself evaluated under randomized physics: 14/20 falls -> `exp0021`'s 7/20; survival 10.3s -> 16.3s), at a real but moderate clean-physics cost (`dist_ratio` 0.709 -> 0.609, ~14% relative; falls unaffected, still 0/20). Warm-starting worked here too -- no exploit, no collapse -- though `approx_kl`/`clip_fraction` ran noticeably hotter by the end of training (0.05-0.08 / 0.48-0.59) than typical reward-term fine-tunes (usually <0.03), suggesting domain randomization is a "larger" distribution shift for this technique than adding a single reward term, worth a lower LR if pushed further. **`experiments/runs/exp0021_dr_on_canonical/best_checkpoint_6M.zip` is adopted as a fourth documented Pareto-surface alternative** (a robustness axis, alongside `exp0018`'s stride length and `exp0019`'s heading control), superseding `exp0015` for anyone who wants DR robustness without giving up the stepping-quality fix; `exp0015` is kept for history. `exp0017` remains canonical. Full writeup: `experiments/EXPERIMENT_LOG.md` EXP-0021.

**Third resolution (2026-09-19, EXP-0029, after canonical moved to `exp0026`, ADR-011):** re-ran the identical recipe again on the new, substantially better canonical. Result: an even stronger robustness gain than EXP-0021's own -- randomized-physics falls drop 14/20 -> 4/20 (71% relative reduction, vs. EXP-0021's 50%) and survival nearly doubles (10.2s -> 18.8s, an 84% increase, vs. EXP-0021's 58%), at a real clean-physics cost (`dist_ratio` 0.918 -> 0.643) that still leaves this DR checkpoint tracking better under clean physics than the *old* canonical `exp0017` ever did. This lineage showed the same early-peak fragility as `exp0026`'s own descendants (EXP-0027/0028) -- clean-physics falls reappear from 8M onward -- but the 6M checkpoint is unambiguously the best point on both conditions simultaneously, not a fragile one-off. **`experiments/runs/exp0029_dr_on_exp0026/best_checkpoint_6M.zip` supersedes `exp0021` as the project's robustness-axis alternative.** `exp0026` remains canonical (clean-physics tracking is still meaningfully better without DR). Full writeup: `experiments/EXPERIMENT_LOG.md` EXP-0029.

## ADR-007 — Canonical baseline updated: warm-start fine-tuning fixed the chattery-stepping problem
Status: decided (2026-09-18).

Context:
F-0004 (docs/FAILURE_ANALYSIS.md) recorded two failed attempts at fixing chattery, ~20ms-median stepping: `feet_air_time_bonus` alone got gamed into a skating gait; adding `stance_overrun_penalty` to close that loophole caused a 100% fall rate. Both trained the new reward term *from scratch*, alongside the policy's own random initialization.

Decision:
Built a warm-start capability (`training/train.py --init-from <checkpoint> --init-learning-rate <lr>`, a real capability gap this project's own docs had flagged as missing) and fine-tuned from `exp0011`'s established, already-stepping checkpoint with `feet_air_time_bonus` alone, at a reduced learning rate (5e-5, confirmed necessary via a smoke test showing `approx_kl` dropping from 0.86 to 0.028). Result: median swing duration doubled (20ms -> 40ms, directly measured, not inferred from reward), with every other metric (survival, reward, velocity-tracking error, falls, yaw drift) matching or improving on `exp0011`. `experiments/runs/exp0016_warmstart_air_time/best_checkpoint_4M.zip` is now the **canonical baseline**.

Why:
The skating exploit was never inherent to the reward term itself -- it was a consequence of encountering that reward before any real stepping behavior existed to protect. An established policy has real reward (tracking + alive bonus flowing through working stepping) to lose by switching strategies, which a freshly-initializing policy does not. This is conceptually a curriculum (walk first, then refine stride quality), implemented via warm-start rather than a staged single training run.

Rejected alternative interpretation:
"The two-term reward combination itself is unsalvageable" (the conclusion after EXP-0013) -- rejected because the *single* term (`feet_air_time_bonus` alone, unmodified from EXP-0012) now works correctly once trained on top of an established policy; the earlier failures were about *how* the reward was introduced to training, not fundamentally about the reward's design.

Consequences:
- `training/train.py`'s `--init-from`/`--init-learning-rate` flags are now a standing capability for any future reward change: introduce it via fine-tuning from the current canonical baseline, at a reduced learning rate, rather than from scratch, especially for a reward term that risks an easy degenerate escape.
- A secondary, unplanned finding: fine-tuning at a low learning rate produced a smooth, steadily-improving training curve with none of the climb-crash-recover oscillation that characterized every from-scratch run in this project (F-0002) -- suggestive that the oscillation itself may be partly a consequence of the large learning rate needed for random-initialization training, not an unavoidable property of this task. Not confirmed as a general fix (only observed on this one fine-tuning run), but worth testing directly (e.g. does `baseline0001`-style config training converge more smoothly at 5e-5 from scratch, just slower?) if pursued further.
- Swing duration, while doubled, remains short of a fully deliberate human-scale stride (40ms median vs. a plausible 200-300ms target) -- an honest, smaller residual limitation. The clear next lever, if pursued: repeat this same warm-start recipe again from the new checkpoint, or raise `feet_air_time_threshold_s` now that the mechanism is known to work.

## ADR-008 — Canonical baseline updated again: continued fine-tuning reached the best result of the project (0/20 falls)
Status: decided (2026-09-18).

Context:
ADR-007 established warm-start fine-tuning as a working fix for chattery stepping, but `exp0016`'s 40ms median swing time was still far below the reward's own `feet_air_time_threshold_s=0.2` (200ms) target -- every touchdown was still being penalized for falling short, suggesting room to keep improving with more of the same recipe.

Decision:
Continued fine-tuning the same lineage -- warm-started from `exp0016`'s own checkpoint, identical config and learning rate (5e-5), for 10M more timesteps (EXP-0017). Result: `dist_ratio` improved further to 0.709 (from 0.627), velocity-tracking error dropped to 0.061 m/s (from 0.086), and **all 20/20 evaluation episodes survived the full 20s with zero falls** -- the first time any run in this project achieved that. Swing duration itself plateaued (median stayed at 40ms; mean and consistency improved, more of the distribution shifted into a tight 40-60ms band, but the ceiling didn't move). `experiments/runs/exp0017_warmstart_air_time_long/best_checkpoint_8M.zip` is now the **canonical baseline**.

Why:
This confirms the fine-tuning recipe generalizes beyond a single short run -- it isn't a one-off lucky result, and the smooth training curve held across the full 10M timesteps (2x EXP-0016's own duration), reinforcing the ADR-007 observation about avoiding the from-scratch PPO oscillation. It also cleanly separates two different things that looked conflated in EXP-0016: "does the policy keep improving" (yes, substantially) and "does swing duration keep increasing" (no, it plateaued) -- more training budget was not simply buying more of the same improvement, it was refining tracking precision and consistency around an already-established stride pattern.

Consequences:
- Swing duration plateauing at ~40-60ms (not the reward's own 200ms target) means the next lever for a more human-like stride is raising `feet_air_time_threshold_s` itself and repeating the fine-tune, not simply spending more budget at the current threshold -- untested, a clear next step if pursued.
- The distinction between "reward/tracking quality" and "the specific behavior a reward term targets" plateauing independently is a general lesson: a single eval metric (or even `dist_ratio`) improving does not mean every underlying mechanism it depends on is still improving -- check the specific mechanism directly (as `diagnostics/gait_diagnostic.py` was built to do), not just the aggregate.
- Wall-clock cost was substantial (~3.5 hours for this one run, with throughput degrading over time -- likely machine load/thermal effects from many consecutive long runs this session) -- a real practical constraint worth noting for anyone continuing this work on similar hardware.

## ADR-009 — Chattery-stepping fix concluded: found a Pareto frontier, not a further clean win
Status: decided (2026-09-18).

Context:
ADR-008 left one clear next lever: push `feet_air_time_bonus` harder (measured-first, doubled 3.0 -> 6.0) to see if swing duration would keep increasing past its plateau.

Decision:
It did -- median swing duration rose from 40ms to 60ms (EXP-0018), a real, measured, further improvement, tripling the original pre-fix baseline (20ms) overall. But this came at a real, not-negligible cost: `dist_ratio` (ADR-003's own north-star "is it actually walking" metric) dropped 23% relative (0.709 -> 0.548), real distance covered fell (3.01m -> 2.51m), and the controlled straight-line diagnostic (built for F-0003) showed heading control measurably worse at every checkpoint checked (11.6 -> 28-65 deg/10s). **Not promoted** -- `exp0017_warmstart_air_time_long` remains canonical. `exp0018`'s checkpoint is kept as a documented alternative (same treatment as the domain-randomization variant, ADR-006) for anyone who specifically values stride length over tracking/heading precision.

Why:
Longer, higher steps at the same control frequency and PD gains plausibly require more corrective effort to stay balanced and on-heading -- effort that competes with the tracking and heading objectives already tuned into the reward. This is a genuine Pareto trade-off (more of one desirable property costs another), not a bug or a miscalibration to fix with a different weight.

Consequences:
- The chattery-stepping problem (F-0003/F-0004) is considered **adequately resolved** for this project's purposes -- swing duration tripled from the original baseline (20ms -> 60ms peak, 40ms at the canonical operating point) with `exp0017` representing the best-verified balance point found across this whole investigation (EXP-0010 through EXP-0018).
- Further pushing this specific lever (weight or threshold) is not expected to yield another clean win without also addressing what makes longer strides cost heading control -- e.g. re-strengthening `ang_vel_penalty` in tandem with a higher `feet_air_time_bonus`, or increasing PD gains for more corrective authority during longer swings. Both untested, left as concrete future directions rather than pursued speculatively.
- This is also a methodological confirmation: not every "the metric moved in the intended direction" result is a win -- check the metrics that matter most (here, `dist_ratio` and the controlled heading test) before declaring one, exactly as ADR-003 and F-0003's own diagnostic were built to enforce.

## ADR-010 — Partially resolved the ADR-009 trade-off with a better-targeted reward term; final state is a genuine 3-way Pareto surface
Status: decided (2026-09-19).

Context:
ADR-009 found that pushing `feet_air_time_bonus` harder for longer strides degraded heading control, and left "re-strengthen `ang_vel_penalty` in tandem" as an untested next lever. Before trying that, measured whether `ang_vel_penalty` (instantaneous rotation-rate squared) was even the right lever: replayed both the good-heading (`exp0017`) and bad-heading (`exp0018`) gaits through the *same controlled straight-line test* and computed mean heading-deviation-squared directly (not the ang_vel proxy) -- 0.038 vs. 0.112, a real 3x gap. This suggested a term that penalizes net drift directly, not rotation-rate magnitude (which can't distinguish a small steady bias from a larger zero-mean oscillation), would be better-targeted.

Decision:
Added `heading_deviation_penalty` (deviation from the heading at episode start, `envs/g1_walk_env.py` tracks `_yaw_at_reset`), calibrated the same measure-first way (weight 0.5, costing the two reference gaits 0.019 and 0.056/step respectively). Fine-tuned from `exp0018`'s longer-stride checkpoint (EXP-0019, 8M timesteps) then continued that lineage further (EXP-0020, 8M more) to test the budget question per the ADR-004/008 precedent. Result: `exp0019`'s checkpoint achieves the best heading of any checkpoint in this project (-7.5 deg/10s on the controlled test, better than `exp0017`'s own -19.0 deg) while matching `exp0018`'s longer strides (60ms median swing) -- confirming the mechanism works and is better-targeted than `ang_vel_penalty` alone. EXP-0020 showed this specific lineage has plateaued (oscillating, not improving, with more budget), unlike the base-gait case.

Why:
This is a genuine, if partial, success: the *specific* problem ADR-009 identified (does the current reward have a term that can even represent "hold heading" independent of "don't rotate fast," and does adding one help) is answered yes. But `exp0019` doesn't fully match `exp0017` on tracking precision (`dist_ratio` 0.613 vs. 0.709, `vel_err` 0.093 vs. 0.061) -- so this does not collapse the three properties (tracking precision, stride length, heading control) into one dominant checkpoint.

Rejected alternative interpretation:
"This fully resolves ADR-009's trade-off, promote `exp0019` as canonical" -- rejected because `exp0019` is worse than `exp0017` on the metrics the deliverable's own primary walking-quality claims rest on (`dist_ratio`, `vel_err`), even though it is better on heading. Promoting it would trade a metric the project has treated as most important (ADR-003) for one that's presented as secondary (though real and worth having).

Consequences:
- **Final state of this whole investigation (EXP-0010 through EXP-0020): a documented 3-way Pareto surface**, not a single best checkpoint. `exp0017_warmstart_air_time_long` remains canonical (best tracking precision, 0/20 falls). `exp0018_air_time_v3` (longest stride, 60ms) and `exp0019_heading_hold` (best heading + long stride, weaker tracking) are both kept as documented alternatives representing different deliberately-chosen trade-off points, exactly as `exp0015`'s domain-randomization variant already is.
- Untried further directions if this is revisited: increasing PD gains for more corrective authority during longer swings (ADR-009's other suggestion) -- **tested and ruled out (2026-09-19)**: measured per-joint torque as a fraction of each actuator's `actuatorfrcrange` across all three checkpoints (`exp0017`/`exp0018`/`exp0019`) under the controlled straight-line test; peak usage never exceeds ~63% of any joint's torque limit, and 0% of steps exceed 90% -- there is no torque headroom being hit, so raising PD gains would not relieve an actuation bottleneck that doesn't exist. The real limiting factor is more likely the balance/timing dynamics of a longer single-support phase itself (a harder *coordination* problem, not an insufficient-torque problem) -- increasing PD stiffness might still change tracking responsiveness for other reasons, but not for the "not enough force available" reason ADR-009 speculated.
- **A longer combined curriculum from scratch with all terms present from early on -- tested and disconfirmed, more strongly than expected (2026-09-19, EXP-0022/0023/0024)**: EXP-0022 trained `exp0019`'s exact reward/PPO config (`feet_air_time_bonus=6.0` + `heading_deviation_penalty=0.5`) from random initialization for 20M timesteps at the standard `learning_rate=3e-4` (no warm start). It never discovered real locomotion at all -- every checkpoint's `dist_ratio` stayed in the 0.04-0.12 range (vs. `exp0017`'s 0.71) despite near-zero falls, because the policy stood in place (final pelvis height ~0.78) and swayed (yaw drift 20-48 deg/10s) while translating only 0.2-0.4m over a full 20-second episode -- the same "alive but not walking" degenerate optimum first found in EXP-0006/F-0002, this time reached via persistently high, never-settling KL (0.09-0.21) rather than KL-capped stability. This raised a natural question: was the *learning rate* the cause (fixable), or the *reward richness* itself (not fixable this way)? EXP-0023 showed low LR (5e-5) alone fixes the oscillation for the *simple* reward (smooth curve, best-in-project tracking, though with a real stepping-quality caveat -- see the dedicated addendum below). EXP-0024 then tested the actual combination: the full rich reward, from scratch, at that same low LR. Result: **an even more complete collapse than EXP-0022's** -- `dist_ratio` 0.014-0.032 across the whole 20M-step trend, and direct inspection showed `distance_traveled_m` of only 0.04-0.05m over an entire episode (vs. EXP-0022's 0.2-0.4m) with near-zero yaw drift (0.17-0.75 deg/10s, an order of magnitude below EXP-0022's swaying) -- a perfectly frozen stance, not even swaying. **Learning rate is decisively not the operative variable in this collapse; the reward's own local-optimum structure is.** `heading_deviation_penalty`/`ang_vel_penalty`/`torque_penalty`/`action_rate_penalty` are all trivially, perfectly minimized by never moving at all, making "stand still" a strongly-attracting optimum from random init regardless of how stably or noisily it is approached. **The sequential fine-tuning chain (`exp0011`->`exp0016`->`exp0017`->`exp0018`->`exp0019`) is not a convenient shortcut to the same destination -- across every LR tried, it is the only method that reliably avoids this trap**, because it starts already far from the "stand still" basin rather than needing to escape it during training. Full writeup: `experiments/EXPERIMENT_LOG.md` EXP-0022/EXP-0023/EXP-0024.
- This concludes the chattery-stepping-and-heading investigation for this project, including every item PROJECT_STATE.md had flagged as an untested lever (PD gains, from-scratch curriculum, and -- resolved along the way -- whether low LR alone avoids the from-scratch PPO oscillation). See the dedicated addendum below for the low-LR finding's own, separate caveat (excellent tracking, but a real stepping-quality regression, caught only by the controlled gait diagnostic).

**Addendum -- does low LR alone (no reward richness) avoid the oscillation, and is that actually good news? (2026-09-19, EXP-0023):** yes and no. Isolating LR as the only variable (`config/default.yaml`'s minimal reward, random init, `learning_rate=5e-5`) produced a smooth, non-oscillating training curve (`approx_kl` never exceeded 0.061, vs. `baseline0001`/`exp0009`'s typical 0.09-0.19) and the best pure-tracking checkpoint in the project (`dist_ratio=0.848`, `vel_err=0.035`, both better than canonical `exp0017`). But the controlled gait diagnostic (`diagnostics/gait_diagnostic.py`) -- not any aggregate metric -- caught a real regression: a 1.2cm foot-lift amplitude, visibly flatter than canonical's already-modest 3cm range, reproducing the exact small/chattery-stepping problem F-0003/F-0004 were built to fix. This is not a contradiction of EXP-0016 through EXP-0020's work -- this run's reward has no `feet_air_time_bonus` term, so nothing asked for a longer stride. **The generalizable lesson: a stable, well-converging optimizer and a good gait are different claims** -- low LR answers "did training find a reliable optimum for what the reward asks for," not "does the reward ask for the right thing." Not promoted at the time; kept as a documented data point (best tracking precision, worst stride quality) -- **but see ADR-011: this checkpoint turned out to be the missing ingredient for finally resolving the Pareto surface below, not just a curiosity.** Full writeup: `experiments/EXPERIMENT_LOG.md` EXP-0023, `docs/FAILURE_ANALYSIS.md` F-0002.

## ADR-011 — Canonical baseline updated: the 3-way Pareto surface (ADR-009/010) is resolved by fine-tuning onto a better base gait, not fundamental to the reward
Status: decided (2026-09-19).

Context:
ADR-009/010 characterized a genuine 3-way trade-off (tracking precision vs. stride length vs. heading control) across every checkpoint descended from the sequential fine-tuning chain `exp0011` -> `exp0016` -> `exp0017` -> `exp0018` -> `exp0019`, and concluded it was a property of the reward family, not a remaining gap. EXP-0023 (this session, ADR-010 addendum) found that a from-scratch run at low LR (5e-5, instead of the standard 3e-4 every earlier base gait was trained with) reaches a substantially better tracking optimum (`dist_ratio=0.848` vs. `exp0011`'s 0.671) -- with a real, but separate, stepping-quality regression. This raised an obvious question: what happens if the *established, already-proven* stepping-quality fine-tuning recipe (ADR-007, `feet_air_time_bonus` via low-LR warm-start) is applied to *this* better base instead of to `exp0011`?

Decision:
EXP-0025 (5M-timestep probe) confirmed the recipe generalizes -- a real stride reappeared (swing duration and foot-lift amplitude matching canonical's own, verified via the mandatory gait diagnostic) while most of the superior tracking was retained, with one real but modest regression (controlled-heading test worse than canonical's best). EXP-0026 (10M more timesteps, same recipe) found the lineage actually peaks early: its 2M checkpoint dominates -- `dist_ratio=0.918` (best in the project, vs. `exp0017`'s 0.709), `vel_err=0.036` (vs. 0.061), 0/20 falls (tied), full-eval yaw drift 17.6 deg/10s (best of any real-walking checkpoint, vs. 36.3), and a 60ms median swing duration matching `exp0018`/`exp0019`'s own best-in-project stride length, all directly measured and visually confirmed via the controlled diagnostic, not just aggregate metrics.

Why:
Every previous point on the Pareto surface inherited the tracking ceiling of its `exp0011` ancestor -- a from-scratch, standard-LR base gait. Fine-tuning can shift the trade-off between properties, but it cannot exceed the ceiling of what the base policy already does well, since low-LR fine-tuning by design makes only small departures from its starting point (that is precisely why it avoids the from-scratch exploit/collapse problem, ADR-007). EXP-0023 raised that ceiling substantially by using a different *base-training* technique (low LR from scratch, not just low LR for fine-tuning). Combining the two techniques -- a better base, fine-tuned with the established stepping-quality recipe -- compounds rather than trades off, because the fine-tuning step no longer has to choose between the base's tracking quality and a new stride; it inherits a better tracking quality to begin with and only has to add the stride on top.

Consequences:
- **`experiments/runs/exp0026_air_time_on_exp0023_long/best_checkpoint_2M.zip` is promoted to canonical baseline**, superseding `exp0017_warmstart_air_time_long` -- the first canonical-baseline change since ADR-008. It beats `exp0017` on tracking (`dist_ratio`, `vel_err`), both heading measures, and matches the best stride length in the project (`exp0018`/`exp0019`'s 60ms) -- a near-total win, not a trade along the old surface. The one remaining gap: `exp0019`'s controlled-heading measurement (-7.5 deg/10s) is still better than this checkpoint's (-14.1 deg/10s), though this checkpoint beats `exp0019` on every other axis including full-eval heading.
- `exp0017`, `exp0018`, `exp0019` are kept for the historical record (each was a genuine best-known-result or informative documented alternative at the time reached) -- not deleted, per this project's standing practice of preserving every meaningfully-informative checkpoint.
- This lineage (`exp0025`/`exp0026`) itself peaks at 2M timesteps and does not improve with more budget (unlike every prior fine-tuning extension in this project) -- a real, noted limit, not further pursued without a new hypothesis.
- Methodological lesson: **the quality of a base policy bounds what any fine-tune built on it can achieve; the base-training technique itself (not just the fine-tuning recipe) is a lever worth improving.** This reframes ADR-009/010's "Pareto surface" finding -- it characterized a real trade-off for one specific base-training lineage, correctly and rigorously, but that lineage's own limitations (not a fundamental property of the reward family) turned out to be the binding constraint. Untried further directions: fine-tune `heading_deviation_penalty` (ADR-010's recipe) onto this new checkpoint to see if the remaining controlled-heading gap closes too; or improve the base-training step itself further (a longer/more careful low-LR-from-scratch run) before applying this fine-tune, to test whether the ceiling can be raised again.

**Follow-up (2026-09-20, EXP-0030/0031):** both untried directions above were tested. Extending `exp0023`'s base training for 10M more timesteps (EXP-0030) did not raise the tracking ceiling -- no checkpoint beat the original 8M-timestep peak (0.848); the trend settled into a noisier, *lower* plateau instead, unlike the standard-LR budget-extension precedent (EXP-0009) that found new higher peaks. The base-training-budget lever is exhausted for this specific recipe.

Fine-tuning `heading_deviation_penalty` onto `exp0026` (EXP-0027/0028, weight varied at 2.0 and 1.0, both at the standard 5e-5 fine-tune LR) never reached 0/20 falls at any checkpoint past a brief 1M-timestep near-miss, regardless of weight -- `exp0026` sits at a fragile, narrow optimum where introducing any new term destabilizes it. EXP-0031 tested the untried variable: the same weight (2.0) that showed the most promise, but a 5x lower fine-tune LR (1e-5 instead of 5e-5). This worked for stability -- falls reached and held 0/20 from 2M through 3M timesteps, the first time any heading fine-tune onto `exp0026` achieved this -- and `dist_ratio` reached 1.099, the best in the project. But it did not close the originally-targeted gap: `vel_err` regressed substantially (0.036 -> 0.061) and the controlled-heading result was inconclusive (noisy across checkpoints, not clearly better than `exp0026`'s own -14.1). **Generalizable lesson: when fine-tuning onto a fragile/narrow optimum, a lower learning rate is the correct fix for instability, not a lower reward weight** -- the two control different things (how much the new term matters vs. how far the optimizer is allowed to move per step) and this project had not previously distinguished them. Not promoted to canonical (a genuine trade-off, not a strict win); kept as a new documented alternative (`experiments/runs/exp0031_heading_on_exp0026_lowlr/best_checkpoint_3M.zip`) representing the best raw distance-coverage checkpoint in the project. This closes the heading-gap investigation (three attempts, EXP-0027/0028/0031) without achieving its original specific goal, but leaves a reusable methodological lesson for any future fine-tuning in this project. Full writeups: `experiments/EXPERIMENT_LOG.md` EXP-0030/EXP-0031.
